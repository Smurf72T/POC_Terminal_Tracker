# Эксплуатация (Ops)

Руководство по эксплуатации POC Terminal Tracker: развёртывание, резервное
копирование, восстановление, мониторинг и обновление.

## 1. Развёртывание

### 1.1. Требования

| Компонент | Версия |
|-----------|--------|
| Windows 10/11 x64 | — |
| PostgreSQL | 14+ (рекомендуется 16/17) |
| pg_dump / psql | из поставки PostgreSQL (должны быть доступны в PATH) |
| Qt 6.2+ | только для сборки из исходников |

### 1.2. Первичная установка

1. Установите PostgreSQL, создайте базу данных:
   ```sql
   CREATE DATABASE pocbase ENCODING 'UTF8';
   ```
2. Разместите файлы приложения в любой каталог (например `C:\Program Files\POC Terminal Tracker\`).
3. Рядом с `POC_Terminal_Tracker.exe` положите:
   - `config\config.json` — конфигурация (см. раздел 2);
   - `.env` — доступ к БД (см. раздел 2);
   - `sql\migrations\` — папку с миграциями БД.
4. Запустите `POC_Terminal_Tracker.exe`. При первом запуске миграции
   `sql\migrations\*.sql` применятся автоматически. После применения миграций
   приложение создаёт учётную запись `admin` со **случайным одноразовым паролем**
   и выводит его один раз в консоль/лог при первом запуске (см. процедуру ниже).

> **⚠️ ВАЖНО (безопасность):** дефолтный пароль `admin` не хранится ни в коде,
> ни в миграциях — при первом запуске генерируется случайный пароль, который
> печатается **один раз** (stdout). Пароль придётся сменить при первом входе
> (приложение принудительно предложит смену). Если приложение уже
> эксплуатировалось со старым дефолтным паролем — смените пароль повторно.

**Получение первоначального пароля `admin`:**
1. Запустите `POC_Terminal_Tracker.exe --check-db` (или обычный первый запуск).
2. В консоли (stdout) будет выведено сообщение вида:
   ```
   Создана учётная запись admin со СЛУЧАЙНЫМ паролем.
   Одноразовый пароль (смените его при первом входе): 8fK3...
   ```
3. Войдите с этим паролем. При входе будет предложена обязательная смена пароля.
4. Если вывод был утерян (например, GUI-запуск без консоли), удалите строку
   `admin` из `tbl_users` (или обнулите `password_hash`), затем повторно запустите
   приложение — пароль будет сгенерирован заново.

### 1.3. Разрешения

- Пользователь БД должен иметь права на создание таблиц/последовательностей
  (миграции), триггеров и функций, а также на чтение служебных каталогов
  (`pg_sequences`, `pg_proc`, …) — для бэкапа.
- Для автобэкапов каталог бэкапов должен быть доступен на запись процессу
  приложения (см. раздел 3.2).

## 2. Конфигурация

Конфигурация лежит в `config\config.json`. Пароль БД передаётся через `.env`
(файл не коммитится в репозиторий). `config.json` тоже не хранится в git —
вместо него коммитится шаблон `config/config.json.example` (содержит версию
приложения и значения по умолчанию, без секретов). Если `config.json` отсутствует,
приложение при старте создаёт его из `.example` (см. `appConfigPath()` в
`src/main.cpp`); при сборке шаблон подставляется в `build/…/config/config.json`
(CMake) — ручное копирование не требуется. Версию для релиза (CPack) и
авто-бамп в CI читают из `config.json.example`.

**SSL:** по умолчанию `sslmode=require` — подключение без TLS отклоняется (защита
от MITM). Для строгой проверки сертификата сервера в продакшене используйте
`sslmode=verify-full` + `sslrootcert` (путь к корневому сертификату CA). Если
локальная БД не настроена на SSL, переопределите режим в `.env`:
`POC_DB_SSLMODE=prefer` (или `disable`) — это локальная разработка, продакшен
должен работать с TLS.

**Пустой пароль:** если `database.password` пуст и не задан `POC_DB_PASSWORD`
в `.env`, приложение при старте выдаст предупреждение в лог, а подключение,
скорее всего, не удастся.

```json
{
  "database": {
    "host": "localhost",
    "port": 5432,
    "database": "pocbase",
    "username": "postgres",
    "password": "",
    "sslmode": "require",
    "sslrootcert": ""
  },
  "application": {
    "name": "POC Terminal Tracker",
    "version": "1.5.3"
  },
  "log_directory": "",
  "backup": {
    "enabled": false,
    "interval_hours": 24,
    "directory": "",
    "retention_count": 14
  },
  "monitoring": {
    "integrity_enabled": true,
    "integrity_interval_hours": 24
  },
  "update": {
    "url": "",
    "check_on_startup": true
  }
}
```

### 2.1. Параметры эксплуатации

| Параметр | По умолчанию | Описание |
|----------|-------------|----------|
| `log_directory` | `""` | Каталог журнала операций. Пусто = `<каталог exe>\logs`; относительный путь резолвится относительно exe. Если каталог недоступен — используется `AppData\Roaming\POC_Terminal_Tracker`. |
| `backup.enabled` | `false` | Включает автоматические бэкапы по расписанию. |
| `backup.interval_hours` | `24` | Периодичность автобэкапов, часы. |
| `backup.directory` | `""` | Каталог автобэкапов. Пусто = `<каталог exe>\backups`. |
| `backup.retention_count` | `14` | Хранить последние N бэкапов (старые удаляются). `0` = хранить все. |
| `monitoring.integrity_enabled` | `true` | Включает автоматическую проверку целостности БД. |
| `monitoring.integrity_interval_hours` | `24` | Периодичность проверки целостности, часы. |

### 2.2. `.env`

```env
POC_DB_HOST=localhost
POC_DB_PORT=5432
POC_DB_NAME=pocbase
POC_DB_USER=postgres
POC_DB_PASSWORD=…
POC_DB_SSLMODE=prefer
POC_DB_SSLROOTCERT=
```

Приоритет: `.env` > `config/config.json`.

**Порядок поиска `.env`** (используется первый существующий файл):

1. `.<каталог exe>/.env`
2. `.<каталог exe>/../.env`
3. `.<каталог config.json>/.env`
4. `.<каталог config.json>/../../.env`

В лог при старте выводится сообщение, какой именно `.env` выбран (или что
`.env` не найден и берутся значения из `config/config.json`).

> **Важно (Linux/Unix):** `.env` содержит секреты (пароль БД). После создания
> установите права `0600`: `chmod 600 .env`. Приложение при старте предупредит
> в логе, если файл доступен на запись группе/остальным. Есть CLI-флаг
> `--fix-env-permissions`, который выполняет `chmod 600` автоматически.

## 3. Резервное копирование

### 3.1. Ручной бэкап

Меню **Сервис → Резервное копирование БД** (только администратор):

1. Укажите путь и имя файла (предложение по умолчанию — `backup_poc_<дата>.sql`).
2. Введите пароль БД.
3. Приоритетно используется `pg_dump` (`--clean --if-exists`, пароль через
   `PGPASSWORD`, без файлов на диске). Если `pg_dump` недоступен, завершился
   по таймауту (60 с) или с ошибкой — автоматически создаётся полный SQL-дамп
   через Qt SQL (fallback): таблицы, последовательности с `setval`, DEFAULT,
   функции, триггеры, индексы, ограничения (FK в конце).

> **Шифрование бэкапов.** Если при создании бэкапа задан пароль, итоговый файл
> шифруется **AES-256-CBC** (`openssl enc -aes-256-cbc -pbkdf2 -iter 100000`)
> и начинается с маркера `POCENC1\n`. При восстановлении приложение распознаёт
> маркер и расшифровывает файл автоматически (для этого требуется `openssl`
> — поиск в PATH, в каталоге приложения, в `C:\Program Files\Git\usr\bin` и т.п.).
> Обычные незашифрованные `.sql`-дампы без маркера восстанавливаются как раньше.
> Пароль не сохраняется на диск — храните его отдельно от бэкапа.

Каждый ручной бэкап записывается в журнал операций (раздел 5).

### 3.2. Автоматические бэкапы (планировщик)

Включаются в `config\config.json`:

```json
"backup": {
  "enabled": true,
  "interval_hours": 24,
  "directory": "backups",
  "retention_count": 14
}
```

- Первый автобэкап выполняется через `interval_hours` после запуска
  приложения, далее — с той же периодичностью.
- **Ограничение:** бэкапы создаются, только пока приложение запущено.
  Для бэкапов в нерабочее время запускайте приложение в это время или
  выполняйте ручные бэкапы. (Для полноценного планирования вне приложения
  можно настроить запуск бэкапа через `pg_dump` средствами Windows
  Task Scheduler — см. раздел 3.4.)
- Имя файла: `backup_poc_<yyyyMMdd_HHmmss>.sql` в каталоге `backup.directory`.
- `retention_count` — после каждого автобэкапа удаляются самые старые
  файлы `backup_poc_*.sql` сверх лимита.
- Пароль для автобэкапа берётся из текущего подключения к БД (`.env`).

Статус последнего автобэкапа отображается в статусбаре главного окна
(«Бэкап: OK / ОШИБКА»), подробности — в журнале операций.

### 3.3. Ручной бэкап через командную строку

```bash
pg_dump -h localhost -p 5432 -U postgres --format=plain --encoding=UTF8 ^
  --clean --if-exists -f backup_poc_20260731_120000.sql pocbase
```

### 3.4. Бэкап через Windows Task Scheduler (рекомендуется для прода)

Так как приложение — десктопное, для гарантированного бэкапа в нерабочее
время настройте задачу Планировщика Windows:

1. Создайте файл `backup.cmd`:
   ```cmd
   @echo off
   set PGPASSWORD=ВАШ_ПАРОЛЬ
   "C:\Program Files\PostgreSQL\17\bin\pg_dump.exe" -h localhost -p 5432 -U postgres ^
     --format=plain --encoding=UTF8 --clean --if-exists ^
     -f "D:\backups\backup_poc_%date:~-4%%date:~3,2%%date:~0,2%_%time:~0,2%%time:~3,2%%time:~6,2%.sql" pocbase
   ```
2. `Планировщик заданий → Создать задачу`:
   - триггер: ежедневно в выбранное время (например 03:00);
   - действие: запуск `backup.cmd`;
   - условия: «Запускать при простое» не обязательно;
   - настройки: «Выполнять при пропуске запуска как можно скорее».
3. Следите за созданием файлов в каталоге бэкапов (или настройте уведомление
   по результату задачи).

## 4. Восстановление

### 4.1. Восстановление из приложения

Меню **Сервис → Восстановление БД из резервной копии** (только администратор).

> ВАЖНО: восстановление полностью заменяет текущие данные. Перед
> восстановлением рекомендуется сделать резервную копию текущего состояния.

- Выберите `.sql`-файл бэкапа, введите пароль БД.
- Восстановление выполняется `psql --single-transaction` (таймаут 120 с):
  при ошибке данные остаются в прежнем состоянии.
- Результат записывается в журнал операций.

### 4.2. Восстановление вручную

```bash
psql -h localhost -p 5432 -U postgres -d pocbase -f backup_poc_20260731_120000.sql
```

При восстановлении поверх существующих данных дамп с `--clean --if-exists`
сначала удалит существующие таблицы.

### 4.3. Восстановление в новую БД

```sql
CREATE DATABASE pocbase_restore ENCODING 'UTF8';
```

```bash
psql -h localhost -U postgres -d pocbase_restore -f backup_poc_20260731_120000.sql
```

## 5. Мониторинг

### 5.1. Журнал операций (`ops.log`)

Все эксплуатационные события записываются в журнал операций
(`logs\ops.log` рядом с exe, либо каталог `log_directory`):

- запуск/остановка приложения;
- ручные и автоматические бэкапы (результат, метод, путь, размер);
- восстановления БД;
- результаты проверки целостности;
- ошибки бэкапов/восстановления.

Формат строки:

```
2026-07-31 12:00:00 [INFO] Автоматический бэкап создан (метод: pg_dump): C:\...\backup_poc_20260731_120000.sql, размер 512 KB
```

Ротация: при превышении 1 МБ текущий файл переименовывается в `ops.log.1`
и журнал продолжается в новом `ops.log`.

Журнал открывается из приложения: **Сервис → Журнал операций**.

### 5.2. Проверка целостности БД

Автоматическая проверка выполняется с периодичностью
`monitoring.integrity_interval_hours` (первая — вскоре после запуска
приложения), а также вручную: **Сервис → Проверка целостности БД**.

Проверяются бизнес-инварианты учёта терминалов и SIM-карт:

| Проверка | Признак проблемы |
|----------|------------------|
| Терминал свободен, но SIM «в аренде» | Нарушение связи статусов |
| SIM «в аренде», но не привязана к терминалу | «Висящая» SIM |
| Терминал «в аренде», но без SIM | Терминал без SIM-карты |

Результат пишется в `ops.log` и показывается в статусбаре.

### 5.3. Что делать при обнаружении несоответствий

1. Откройте **Сервис → Проверка целостности БД** и зафиксируйте перечень
   проблем (в журнале — с примерами записей).
2. Для разовой ручной коррекции используйте `sql\diagnostics.sql`
   (разделы «ИСПРАВИТЬ»). Скрипт изменяет данные — выполняйте его только
   после бэкапа и под контролем администратора.
3. Если проблемы повторяются — проверьте правильность работы
   документов «Передача в аренду» / «Возврат из аренды».

### 5.4. Прочие источники диагностики

- `QLoggingCategory` — см. README (раздел «Логирование»), категории
  `app.database`, `app.audit`, `app.migration`, `app.sql`, `app.general`.
  Включение: `QT_LOGGING_RULES="app.sql=true;app.migration=true"`.
- Вкладка «Подключено к БД» в статусбаре главного окна.
- `tbl_audit_log` — журнал аудита действий пользователей (Сервис → Журнал аудита).

### 5.5. Health-check (`--check-db`)

Безголовый режим проверки подключения к БД и применённых миграций (для мониторинга
и CI, работает без GUI):

```bash
POC_Terminal_Tracker.exe --check-db
```

Коды возврата:
- `0` — `DB_OK`, подключение есть, все миграции применены;
- `1` — `DB_ERROR`, нет соединения или не удалось применить миграции;
- `2` — `DB_WARN`, соединение есть, но есть неприменённые миграции.

Дополнительные флаги: `--version` (вывод версии из `config.json`), `-h`/`--help`.
Ошибки в этом режиме не выводят модальные диалоги (лог в stderr).

## 6. Обновление версии

### 6.1 Портативный дистрибутив

Сборка дистрибутива (Qt runtime, драйвер QPSQL, DLL PostgreSQL, конфиг, миграции, документация):

```bash
cmake --build build --target deploy      # собирает build/deploy/
cpack --config build/CPackConfig.cmake   # POC_Terminal_Tracker-<версия>.zip (+ .exe при наличии NSIS)
```

Пользователь распаковывает ZIP в любую папку и запускает `POC_Terminal_Tracker.exe`.
Конфигурация и БД не хранятся рядом с exe (порт. режим) — настройки подключения
берутся из `.env` рядом с exe, а пароль — из `POC_DB_PASSWORD`.

### 6.1.1 Инсталлятор (NSIS)

При установленном NSIS (`makensis` в PATH) CPack дополнительно соберёт инсталлятор
`.exe`: создаётся пункт меню и ярлык на `docs\OPS.md`. Версия пакета берётся из
`config\config.json`. Имя пакета не содержит суффикс `-portable`:
`POC_Terminal_Tracker-<версия>.zip` / `.exe`.

### 6.1.2 Code signing

- **Локально**: подпись через `osslsigncode` включается опциями конфигурации
  `-DPOC_SIGNING=ON -DPOC_SIGNING_PFX=<путь>.pfx -DPOC_SIGNING_PASSWORD=<пароль>`
  и выполняется на этапе сборки (POST_BUILD: подпись → копирование → удаление).
- **В CI**: подпись выполняется через `Import-PfxCertificate` +
  `Set-AuthenticodeSignature`, если заданы секреты `CODE_SIGN_PFX_BASE64`
  (PFX в base64) и `CODE_SIGN_PASSWORD`; без секретов шаг пропускается.
- Проверить подпись: `Get-AuthenticodeSignature POC_Terminal_Tracker.exe`.

### 6.1.3 Linux CI и code coverage

CI на Linux (`.github/workflows/linux.yml`): сборка на Ubuntu + прогон всех тестов
(включая `test_db_integration`/`test_concurrency` против реального PostgreSQL).
Отдельная джоба собирает проект с флагами `--coverage -O0` и публикует отчёт gcovr
(артефакт + Codecov при заданном секрете `CODECOV_TOKEN`).

### 6.1.4 Внутренняя документация и версионирование

- **API-документация**: `docs/API.md` — сигнатуры и контракты внутренних модулей
  (`DatabaseManager`, `ConnectionPool`, `BackupManager/BackupWorker`, `OpsScheduler`,
  `CircuitBreaker`, `password_utils`, CLI-режимы, тесты).
- **ADR**: `docs/adr/ADR-0001.md` — 5 записей (ADR-0001…0005): обоснование ключевых
  архитектурных решений (БД, пароли, фоновый бэкап, конвенция делегатов, доставка/подпись).
- **QXlsx**: версия зафиксирована commit'ом субмодуля (`8a13e1c8` в `.gitmodules`);
  обновление — только осознанным переводом указателя субмодуля и прогоном тестов.
- **Версионирование**: версия хранится в `config/config.json`
  (`application.version`). При push в `master` CI автоматически увеличивает patch-номер
  и дописывает запись в `CHANGELOG.md` (см. `.github/workflows/ci.yml`, джоба
  `bump-version`). Сборка/тесты выполняются для версии из коммита.

### 6.2 Ручное обновление

1. Сделайте бэкап БД (раздел 3).
2. Остановите приложение.
3. Замените файлы приложения (exe, DLL, `sql\migrations\`, `config\`).
   Сохраните `.env` и `config\config.json` (или перенесите настройки).
4. Запустите приложение — новые миграции из `sql\migrations\` применятся
   автоматически.
5. Проверьте журнал операций на успешность применения миграций
   (`app.migration`), выполните проверку целостности БД.

Если авто-миграции не сработали (нет прав), примените новые миграции вручную
в порядке нумерации:

```bash
psql -U postgres -d pocbase -f sql\migrations\00X_xxx.sql
```

### 6.3 Автообновление (в приложении)

Приложение умеет проверять наличие новой версии по HTTP-манифесту, скачивать
дистрибутив и устанавливать его самостоятельно. Настройка в `config\config.json`:

```json
"update": {
  "url": "https://example.com/poc/update.json",
  "check_on_startup": true,
  "pinned_sha256": ""
}
```

> `check_on_startup` устарел: стартовую проверку теперь управляет переключатель
> «Автообновление» в окне «Сервис → Проверка обновлений» (настройка хранится
> в реестре, QSettings).

Формат манифеста:

```json
{
  "version": "1.4.1",
  "release_notes": "Что изменилось",
  "download_url": "https://example.com/poc/POC_Terminal_Tracker-1.4.1-portable.zip",
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
}
```

- Поле `sha256` (hex, 64 символа) опционально, но **настоятельно рекомендуется**:
  после скачивания приложение проверяет контрольную сумму архива и отклоняет
  файл при несовпадении (защита от повреждения/подмены при передаче).
  Пример генерации: `Get-FileHash POC_Terminal_Tracker-1.4.1-portable.zip -Algorithm SHA256`.
- `pinned_sha256` — отпечаток публичного ключа сервера (base64 SHA-256 от
  SubjectPublicKeyInfo сертификата, 44 символа). Опционально, но **настоятельно
  рекомендуется** для HTTPS: при включении приложение проверяет сертификат
  сервера при загрузке манифеста и скачивании и отклоняет обновление, если
  отпечаток не совпадает (защита от MITM даже при скомпрометированных корневых
  сертификатах). Пример генерации:
  ```bash
  openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
    | openssl x509 -pubkey -noout \
    | openssl pkey -pubin -outform DER \
    | openssl dgst -sha256 -binary \
    | openssl enc -base64
  ```
  Если `url` начинается с `http://`, а pin задан — проверка будет отклонять
  запросы (используйте HTTPS).
- Меню «Сервис → Проверка обновлений» открывает окно **«Обновления»**:
  - переключатель **«Автоматически проверять и устанавливать обновления»**;
  - при включённом автообновлении программа при запуске сама проверяет,
    скачивает и устанавливает новую версию, показывая актуальную версию
    в заголовке окна и в статусбаре;
  - при выключенном — доступны кнопки **«Проверить обновление»** и
    **«Обновить»** (появляется, если найдена новая версия).
- Установка: архив скачивается в `<каталог приложения>\update\`, проверяется
  контрольная сумма, затем запускается скрипт установки: он дожидается
  завершения приложения, распаковывает архив поверх каталога приложения
  (`.env` и рабочий `config\config.json` сохраняются) и перезапускает exe.
- **HTTPS обязателен:** `update.url` (и `download_url` в манифесте) принимаются
  только по HTTPS. `http://` допустим лишь для `localhost`/`127.0.0.1` (локальная
  отладка). При несоответствии автообновление отключается с ошибкой в логе —
  это защита от MITM даже при пустом `pinned_sha256`.
- При пустом `update.url` проверка отключена (окно обновлений сообщит об этом).

## 7. Многопользовательский режим

Приложение рассчитано на одновременную работу нескольких пользователей
(несколько запущенных экземпляров) с общей базой PostgreSQL.

### 7.1. Защита от гонок

| Сценарий | Механизм защиты |
|----------|-----------------|
| Одновременный первый запуск нескольких экземпляров | Миграции применяются под `pg_advisory_lock` («POCMIGR»): второй экземпляр ждёт завершения миграций первым, дубли версий невозможны |
| Выдача одной SIM-карты двум терминалам | Аренда блокирует строку SIM `SELECT ... FOR UPDATE NOWAIT` с проверкой статуса = 0; проигравшая транзакция откатывается с сообщением |
| Потерянное обновление при массовой смене статуса | `BatchStatusForm` блокирует терминал `FOR UPDATE NOWAIT` и проверяет, что статус не изменился после загрузки списка |
| Обход rate limiting при параллельных попытках входа | Сброс истёкшей блокировки и инкремент счётчика — один атомарный UPDATE; при активной блокировке попытки отклоняются |
| Перезапись чужих изменений | Номера документов — через `nextval()` (атомарно, без дублей); редактирование документов выполняется в транзакции с блокировкой строк |

### 7.2. Межэкземплярное обновление

Триггеры (миграция `007_data_change_notify.sql`) после изменения любой бизнес-
таблицы отправляют `NOTIFY poc_data_changed`. Приложение подписано на канал и при
получении уведомления обновляет дашборд (счётчики, топ-клиенты, последние
документы). Дополнительно дашборд обновляется по таймеру каждые 30 секунд.
Списки-справочники перечитываются при открытии формы.

> Примечание: `NOTIFY` доставляется только после `COMMIT`, поэтому уведомления
> приходят исключительно о зафиксированных изменениях.

### 7.3. Конкуренто-тесты

Набор `tests/test_concurrency.cpp` (таргет `test_concurrency`, запускается через
`ctest`): каждый поток использует собственное соединение с БД.
Сценарии: генерация 400 номеров в 8 потоках, гонка выдачи одной SIM (ровно 1
успех из 8), параллельные аренды без дублей, гонка «массовая смена vs аренда»,
rate limiting (ровно 5 пробивающих попыток из 20), одновременное применение
миграций двумя «экземплярами».

## 8. Диагностика проблем

| Проблема | Причина / решение |
|----------|-------------------|
| Автобэкап не выполняется | `backup.enabled=false`; приложение не было запущено в момент срабатывания; каталог бэкапов недоступен на запись. Проверьте `ops.log`. |
| «pg_dump не найден» / бэкап всегда fallback | Добавьте `C:\Program Files\PostgreSQL\<версия>\bin` в PATH или настройте Task Scheduler (раздел 3.4). |
| Ошибка подключения при старте | Проверьте PostgreSQL-сервис (`postgresql-x64-17`), `.env`, `sslmode`. |
| «Роль не может выполнить INSERT» | Не хватает прав пользователя БД (см. раздел 1.3). |
| Журнал операций пуст | Путь из `log_directory` недоступен — проверьте права на запись; фактический путь выводится в статусбаре при открытии журнала. |
| Ошибки целостности при каждой проверке | Выполните коррекцию через `sql\diagnostics.sql` (раздел 5.3). |

## 9. Сканер штрих-кода

Документ «Поступление терминалов» работает со строками вида
«Модель + Кол-во + Серийные номера + IMEI 1 + IMEI 2»: строка описывает серию
устройств одной модели, а при проведении разворачивается в отдельные терминалы.
Сканер штрих-кода помогает заполнять списки серийных номеров и IMEI в строке.

### 9.1. Подключение сканера

- **USB-сканер в режиме клавиатуры (keyboard wedge)** — работает без настройки:
  сканер «печатает» код и шлёт Enter/Tab в конце.
- **Для IMEI** нужен **2D-сканер** (читает QR/DataMatrix): IMEI 1 и IMEI 2
  обычно напечатаны подписями `IMEI1:` / `IMEI2:`.
- COM/TCP-сканеры в MVP не поддерживаются.

### 9.2. Форматы данных

| Что сканируем | Пример | Куда попадёт |
|---------------|--------|--------------|
| Простой серийный номер | `ABC-12345` | Серийный номер |
| Голый IMEI (15 цифр) | `356938035643809` | IMEI 1 |
| Подписанные поля | `SN:ABC-123 IMEI1:356… IMEI2:356…` | все три колонки |
| Общий IMEI | `IMEI:356938035643809` | первая свободная колонка IMEI |

Разделители в подписанных полях — пробел, запятая, табуляция, перевод строки;
GS1-разделители (`\x1D`/`\x1E`) также понимаются.

### 9.3. Правила работы

- Скан обрабатывается, когда **фокус не в текстовом поле** (поле комментария,
  номер документа, редактор ячейки). Оператор держит фокус на таблице — после
  каждого скана фокус автоматически возвращается на таблицу. Если открыто окно
  ввода списка (`SerialListDialog`), сканер пишет прямо в его текстовое поле.
- Сканируемые данные **дописываются в списки выбранной строки**: серийный номер —
  в «Серийные номера», IMEI — в соответствующую колонку. Так оператор
  просканировав пачку устройств в одной строке, заполняет все её номера.
- **Модель и количество задаются в самой строке таблицы** (модель — из
  выпадающего списка в ячейке, по умолчанию первая из справочника).
- Списки номеров вводятся вручную двойным кликом по ячейке — открывается окно
  с текстовым полем «один номер на строку», живым счётчиком «N из M» и
  проверкой дублей (для IMEI также контроль длины 15 цифр и автоочистка
  разделителей `-`/пробелов).
- Валидация при проведении: **число серийных номеров обязательно равно
  количеству**; IMEI — ровно 15 цифр; дубли серийников/IMEI внутри документа и
  уже занятые в базе серийники отклоняются с указанием строки и значения.
- Исходник документа (строки + серийники/IMEI) сохраняется в
  `tblreceiptitems`/`tblreceiptserials` (миграция `012`) — документ можно
  перепечатать «как вводили»; терминалы при этом создаются, как и раньше.
