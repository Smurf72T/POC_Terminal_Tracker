## P0-1. Печать накладной: пустая колонка «Модель» — ✅ ВЫПОЛНЕНО (12.08.2026)

**Проблема:** в `ReceiptForm::on_btnPrint_clicked()` (receiptform.cpp:385-392) при формировании HTML колонка «Модель» читает `DisplayRole` (текст) и конвертирует в `int` (→ 0). ID модели лежит в `Qt::UserRole` (при сохранении, строка 231, читается корректно). В накладной колонка «Модель» всегда пустая.

**Файлы:**
- `src/ui/dialogs/receiptform.cpp`

**Шаги:**
1. Найти `for (int i = 0; i < rowsModel->rowCount(); ++i)` в `on_btnPrint_clicked` (строка ~385).
2. Заменить
   ```cpp
   QString modelIdx = rowsModel->data(rowsModel->index(i, 1)).toString();
   int modelId = modelIdx.toInt();
   ```
   на чтение ID из UserRole, как в `on_btnPost_clicked` (строка 231):
   ```cpp
   int modelId = rowsModel->data(rowsModel->index(i, 1), Qt::UserRole).toInt();
   ```
3. Проверить, что вывод `m_models`-цикла остаётся прежним (сопоставление `m.first == modelId`).
4. Если колонка «Модель» хранит только текст (нет UserRole) — уточнить `loadModelsToDelegate`/`loadForEdit`: при редактировании модель должна заполняться через `setData(..., Qt::UserRole)` с ID.

**Критерии готовности:**
- Сформированный HTML содержит название модели для каждой строки.
- Регресс: сохранение (`on_btnPost_clicked`) по-прежнему валидирует `modelId > 0`.

**Статус:** выполнено. В `on_btnPrint_clicked` чтение ID модели заменено на `Qt::UserRole` (как в `on_btnPost_clicked`); `ComboBoxDelegate::setModelData` и `loadForEdit` уже сохраняют ID в `UserRole`, поэтому название модели корректно попадает в HTML.

**Трудозатраты:** ~0.5–1 ч. Риск: низкий.

## P0-2. «Деактивация» терминала на деле выполняет DELETE — ✅ ВЫПОЛНЕНО (12.08.2026)

**Проблема:** `TerminalsForm::on_btnDelete_clicked()` (terminalsform.cpp:263-275): если на терминал ссылаются документы, UI показывает сообщение «терминал будет деактивирован», но выполняет `DELETE FROM tblterminals`, который падает на `ON DELETE RESTRICT` (`tblreceiptdetails`/`tblrentaldetails`/`tblreturndetails`). Пользователь получает ошибку, терминал остаётся в БД. Флага деактивации нет.

**Файлы:**
- `src/ui/dialogs/terminalsform.cpp`
- `src/ui/dialogs/terminalsform.h`
- `sql/migrations/011_terminals_deactivated.sql` (новая)
- схема `sql/migrations/000_base_schema.sql` (для справки о FK)

**Шаги:**
1. Миграция `011`: `ALTER TABLE tblterminals ADD COLUMN IF NOT EXISTS is_deactivated BOOLEAN NOT NULL DEFAULT FALSE;` + индекс при необходимости. Проверить, что статусная модель не конфликтует (статус `0` = свободен; деактивация — отдельный флаг, не статус).
2. В `loadModel()` (запрос списка) — добавить фильтр/колонку `is_deactivated`; решить: скрывать деактивированные или показывать с пометкой.
3. В `on_btnDelete_clicked`: вместо `DELETE` при наличии ссылок выполнять
   ```sql
   UPDATE tblterminals SET is_deactivated = TRUE WHERE terminalid = :id
   ```
   и убрать вводящее в заблуждение сообщение «будет деактивирован вместо удаления» → «терминал будет помечен как деактивированный».
4. В `on_btnAdd_clicked`/`loadForEdit` — исключить деактивированные терминалы из выбора (при поступлении/аренде).
5. Проверить остальных потребителей: `batchstatusform`, `mainwindow` (поиск), отчёты — не должны включать деактивированные терминалы в «арендуемые».

**Критерии готовности:**
- Терминал с документами помечается `is_deactivated=TRUE` без ошибки.
- Деактивированный терминал не выбирается в новые документы.
- Регресс: физическое удаление терминала без документов по-прежнему работает.

**Статус:** выполнено. Миграция `011_terminals_deactivated.sql` добавляет `is_deactivated` + индекс; `terminalsform` показывает колонку «Деактивирован» и при ссылках выполняет `UPDATE ... SET is_deactivated=TRUE` (а не DELETE) с корректным сообщением; `rentalform`/`batchstatusform` исключают деактивированные терминалы из выбора/массового обновления. Счётчики миграций в тестах обновлены (11 → 12).

**Трудозатраты:** ~3–5 ч. Риск: средний (трогает модель данных).

## P0-5. `getDatabase()` возвращает неконстантную ссылку — ✅ ВЫПОЛНЕНО (12.08.2026)

**Файлы:**
- `src/database/databasemanager.h/.cpp`

**Шаги:**
1. Изменить сигнатуру на `const QSqlDatabase &getDatabase() const;`.
2. Исправить все вызывающие места (компилятор подсветит; их много в UI-формах: `QSqlQuery q(DatabaseManager::instance().getDatabase())` — это совместимо, т.к. `QSqlQuery(const QSqlDatabase&)`).
3. Проверить места, где держат ссылку и вызывают методы, не требующие мутации (например, `db.transaction()` — метод `QSqlDatabase` не const; при необходимости выделить отдельный `beginTransaction()`/`commitTransaction()` в менеджер).

**Критерии готовности:**
- Сигнатура `const QSqlDatabase &`; проект компилируется.
- Ни одна форма не вызывает `close()`/`removeDatabase()` через `getDatabase()`.

**Статус:** выполнено. Сигнатуры `IDatabaseManager::getDatabase()` и `DatabaseManager::getDatabase()` — `const QSqlDatabase&` (метод const). Прямых вызовов `transaction()/close()` через `getDatabase()` нет (все используют локальную копию `QSqlDatabase db = ...getDatabase()`). Проект компилируется; стаб в `tests/stub_databasemanager.cpp` обновлён.

**Трудозатраты:** ~2–3 ч + время на устранение компиляторных ошибок. Риск: средний.
