## [1.5.0] — 2026-07-31

### Multi-user & concurrency
- **Защита миграций от гонки**: `runMigrations()` берёт `pg_advisory_lock` («POCMIGR») — при одновременном старте нескольких экземпляров второй ждёт завершения миграций первым, а не падает с ошибкой
- **Выдача SIM-карты под блокировкой**: аренда теперь блокирует строку SIM `FOR UPDATE NOWAIT` (проверка статуса=0) — две параллельные аренды не могут выдать одну SIM двум терминалам
- **Массовая смена статуса безопасна**: `batchstatusform` блокирует каждый терминал `FOR UPDATE NOWAIT` и проверяет, что его статус не изменился после загрузки списка — массовая смена больше не перезаписывает аренду, проведённую другим пользователем
- **Rate limiting без гонки**: сброс истёкшей блокировки + инкремент счётчика объединены в один атомарный UPDATE с WHERE-условием на активную блокировку — после истечения блокировки атакующий больше не получает «новое окно» на каждую параллельную попытку (ровно 5 попыток за 30 с)
- **Межэкземплярное обновление**: миграция `007_data_change_notify.sql` — триггеры `NOTIFY poc_data_changed` на всех бизнес-таблицах; приложение подписывается на канал и обновляет дашборд при изменениях, сделанных в другом экземпляре (дополнение к 30-секундному таймеру)
- **CHECK-ограничение статусов исправлено**: миграция `006_terminal_status_check.sql` расширяет `CHECK (status IN (0,1,2))` до `(0,1,2,3,4)` — на свежей БД списание/утеря (статусы 3/4) больше не падают с ошибкой

### Tests
- **`test_concurrency`**: новый набор конкуренто-тестов (отдельное соединение на поток):
  - генерация 400 номеров документов в 8 потоках — все уникальны
  - гонка выдачи одной SIM 8 пользователями — успешна ровно 1 операция, состояние консистентно
  - нагрузка: 8 параллельных аренд разных терминалов — все успешны, SIM распределены без дублей
  - гонка «массовая смена статуса vs аренда» — всегда ровно один победитель, без потерянных обновлений
  - rate limiting: 20 параллельных неудачных попыток — ровно 5 пробивают до блокировки
  - миграции: два «экземпляра» одновременно применяют отложенные миграции — обе успешны, без дублей версий
- **`test_db_integration`**: счётчик применённых миграций обновлён на 8

## [1.4.0] — 2026-07-31

### Delivery
- **Портативный дистрибутив**: цель `deploy` (windeployqt) + CPack ZIP `POC_Terminal_Tracker-<версия>-portable.zip` — Qt runtime, драйвер `qsqlpsql`, DLL PostgreSQL (libpq/libintl/OpenSSL), MinGW runtime, `config/`, миграции и документация в комплекте; запуск без установки
- **Автообновление**: `update/updatemanager.*` — проверка манифеста `{"version", "release_notes", "download_url"}` по `update.url` (при старте и «Сервис → Проверка обновлений»), диалог «Скачать/Позже», скачивание в папку загрузок с прогрессом; при пустом `update.url` функция выключена
- **Утилиты версий**: `update/version.h` — `parseVersion`/`compareVersions`/`isVersionNewer` (semver major.minor.patch, `-beta` игнорируется)
- **Тесты**: `test_update_utils` — парсинг и сравнение версий
- **Об About**: версия приложения читается из `config.json` (была захардкожена 1.1.0)

- **Планировщик автобэкапов**: `ops/opsscheduler.*` — автоматические бэкапы по расписанию (`backup.interval_hours`, пока приложение запущено), каталог `backup.directory`, retention `backup.retention_count` (авто-удаление старых `backup_poc_*.sql`), статус в статусбаре главного окна
- **Журнал операций**: `ops/opslog.*` — `logs/ops.log` с записями о запусках, бэкапах, восстановлениях, проверках целостности и ошибках; ротация при 1 МБ; открытие из меню «Сервис → Журнал операций»
- **Мониторинг целостности**: автоматическая проверка бизнес-инвариантов терминалов/SIM (`monitoring.integrity_interval_hours`) + ручной запуск «Сервис → Проверка целостности БД»; результаты в `ops.log`
- **Рефакторинг бэкапа**: логика вынесена из `MainWindow` в `ops/backupmanager.*` (pg_dump + fallback-дамп и psql-restore без UI) — переиспользуется ручным бэкапом и планировщиком
- **Документация**: `docs/OPS.md` — развёртывание, настройка автобэкапов (в т.ч. Windows Task Scheduler), восстановление, мониторинг, обновление, troubleshooting; конфиг `backup`/`monitoring` в `config.json`

## [1.2.1] — 2026-07-31

### Data integrity
- **Чистая установка БД**: миграция `000_base_schema.sql` — базовые бизнес-таблицы, представления и индексы теперь создаются миграциями (ранее схема существовала только в живой БД, из-за чего новая БД была неработоспособна)
- **Кодировка миграций**: раннер читает SQL-файлы явно как UTF-8 (`QStringConverter::Utf8`)

### Backup & Restore
- **Контроль таймаута и кода выхода**: pg_dump завершается по таймауту 60 с (kill + fallback-дамп), результат считается успешным только при `exitCode == 0`; psql restore — таймаут 120 с с инструкцией по ручному восстановлению

### Security
- **Аудит под реальным пользователем**: `logAction` больше не подставлял дефолт `admin` — теперь берётся текущий пользователь сессии
- **Обход смены пароля закрыт**: обновление хэша происходит только после успешной смены пароля (ранее пароль сбрасывался при любом входе с помеченным хэшем)

### Fixes
- **LIKE-фильтры**: экранирование `\`, `%`, `_` в поиске справочников (запросы с `%`/`_` больше не превращаются в подстановочные)

- **Аудит с реальным пользователем**: `set_config('app.username', …)` после входа — записи аудита больше не помечаются как «system»

### Fixes

- **Массовый импорт импортирует весь файл**, а не первые 50 строк предпросмотра; корректные номера строк в ошибках
- **Журнал импорта**: пользователь из сессии вместо хардкода `admin`
