# Changelog

## [1.5.5] — 2026-08-19

### Исправление сканера штрих-кода через COM-порт
- **Утечка хэндла COM-порта в `SerialScanner`** (`src/utils/serialscanner.cpp`):
  обработчик `finished` вешался на «орфановый» `QThread`, а рабочий поток
  создавался отдельным `QThread::create` — при закрытии формы хэндл COM8
  никогда не закрывался, и следующая форма не могла открыть порт на запись.
  Теперь один рабочий поток, хэндл захватывается потоком по значению и
  гарантированно закрывается в `stop()`
- **Индикатор статуса сканера в форме поступления** (`receiptform`): строка
  «Сканер: COM8 (9600 бод) — готов / не удалось открыть / отключен в config.json» —
  приложению сразу видно, доступен ли порт

## [1.5.4] — 2026-08-18

### Учёт серийных номеров в поступлении (в стиле 1С, упрощённый)

- **Строка документа = модель + кол-во + комплекты**: табличная часть
  документа «Поступление терминалов» переработана — строка описывает серию
  устройств одной модели (колонки «Модель», «Кол-во», «Серийные номера»)
  вместо одной строки на терминал; модель и «Сформировать строки» убраны из
  шапки формы (`receiptform`)
- **Комплекты «серийный номер + его IMEI»** (`src/ui/dialogs/serialunitsdialog.*`):
  двойной клик по ячейке «Серийные номера» открывает окно, где **каждая строка —
  один комплект** (серийник и его IMEI 1 / IMEI 2 в одной строке — связь не
  теряется). Авто-переход SN → IMEI 1 → IMEI 2 → следующий комплект, живой
  счётчик «заполнено N из M», проверка дублей и длины IMEI (15 цифр, разделители
  убираются)
- **Логика сканера «SN → IMEI 1 → IMEI 2»** (`BarcodeParser::applyScan`):
  серийник открывает новый комплект, голые IMEI дописываются к последнему
  комплекту (сначала в IMEI 1, затем в IMEI 2) — второй IMEI больше не создаёт
  лишнюю строку; IMEI под подписью `IMEI2:` сразу в слот 2; отсканированный до
  серийника IMEI ждёт SN в той же строке. Если окно комплектов открыто, скан
  идёт прямо в него (и COM-порт, и клавиатурный режим), а не в таблицу документа
- **Сохранение «исходника» документа**: миграция `012_receipt_items_serials.sql`
  — таблицы `tblreceiptitems` (модель + кол-во) и `tblreceiptserials`
  (серийники/IMEI на единицу, `UNIQUE(item, linenum)`); документ можно
  перепечатать «как вводили», терминалы по-прежнему разворачиваются на проведении
- **Проведение**: строгий контроль «число серийников = кол-во», дублей
  серийников/IMEI в документе и уже занятых в базе серийников; редактирование
  обновляет существующие терминалы по серийнику
- **Обратная совместимость**: документы, созданные до `012`, при редактировании
  восстанавливаются группировкой развёрнутых строк по модели
- **Репозиторий/модели**: `DocumentRepository::loadReceiptItems()`,
  `models::ReceiptItem` / `models::ReceiptSerial`; тест `applyScan*` в
  `test_barcodeparser`

## [1.5.3] — 2026-08-03

### Аудит (03.08.2026 — шестой этап: HTTPS, SSL по умолчанию, тесты планировщика)
- **HTTPS обязателен для автообновлений**: `UpdateManager::isSecureUpdateUrl()` — `update.url` и `download_url` принимаются только по HTTPS (`http` допустим лишь для `localhost`); несоответствие отключает автообновление с ошибкой в логе; unit-тест `test_updatemanager`
- **SSL по умолчанию `require`**: `config.json` и фолбэк в `DatabaseManager` — подключение без TLS отклоняется (защита от MITM); для прода рекомендуется `verify-full` + `sslrootcert`; локальная разработка может переопределить режим через `POC_DB_SSLMODE` в `.env`
- **Предупреждение о пустом пароле БД**: при старте логируется предупреждение, если `database.password` пуст и `POC_DB_PASSWORD` не задан
- **CMake-проверка утилит**: предупреждения при отсутствии `pg_dump`/`psql` (fallback-дамп) и `openssl` (нет шифрования бэкапов)
- **Тесты `OpsScheduler`**: `test_opsscheduler` — парсинг конфигурации, отсутствие событий при отключённых фоновых задачах, регистрация метатипа `BackupResult`
- **Исправлен латентный баг**: `BackupResult` не был зарегистрирован для queued-доставки сигнала `BackupWorker::backupFinished` между потоками — автобэкап «зависал» (`m_backupInProgress`), слот `onBackupWorkerFinished` не вызывался; добавлены `Q_DECLARE_METATYPE` и `qRegisterMetaType` в конструкторе `BackupWorker`
- **Согласованность SSL**: фолбэк `sslmode` в `BackupWorker::createRawConnection()` изменён `prefer` → `require`

## [1.5.0] — 2026-07-31

### Multi-user & concurrency
- **Защита миграций от гонки**: `runMigrations()` берёт `pg_advisory_lock` («POCMIGR») — при одновременном старте нескольких экземпляров второй ждёт завершения миграций первым, а не падает с ошибкой
- **Выдача SIM-карты под блокировкой**: аренда теперь блокирует строку SIM `FOR UPDATE NOWAIT` (проверка статуса=0) — две параллельные аренды не могут выдать одну SIM двум терминалам
- **Массовая смена статуса безопасна**: `batchstatusform` блокирует каждый терминал `FOR UPDATE NOWAIT` и проверяет, что его статус не изменился после загрузки списка — массовая смена больше не перезаписывает аренду, проведённую другим пользователем
- **Rate limiting без гонки**: сброс истёкшей блокировки + инкремент счётчика объединены в один атомарный UPDATE с WHERE-условием на активную блокировку — после истечения блокировки атакующий больше не получает «новое окно» на каждую параллельную попытку (ровно 5 попыток за 30 с)
- **Межэкземплярное обновление**: миграция `007_data_change_notify.sql` — триггеры `NOTIFY poc_data_changed` на всех бизнес-таблицах; приложение подписывается на канал и обновляет дашборд при изменениях, сделанных в другом экземпляре (дополнение к 30-секундному таймеру)
- **CHECK-ограничение статусов исправлено**: миграция `006_terminal_status_check.sql` расширяет `CHECK (status IN (0,1,2))` до `(0,1,2,3,4)` — на свежей БД списание/утеря (статусы 3/4) больше не падают с ошибкой

### Tests
- **`test_concurrency`**: новый набор конкуренто-тестов (отдельное соединение на поток):
  - генерация 400 номеров документов в 8 потоках — все уникальны
  - гонка выдачи одной SIM 8 пользователями — успешна ровно 1 операция, состояние консистентно
  - нагрузка: 8 параллельных аренд разных терминалов — все успешны, SIM распределены без дублей
  - гонка «массовая смена статуса vs аренда» — всегда ровно один победитель, без потерянных обновлений
  - rate limiting: 20 параллельных неудачных попыток — ровно 5 пробивают до блокировки
  - миграции: два «экземпляра» одновременно применяют отложенные миграции — обе успешны, без дублей версий
- **`test_db_integration`**: счётчик применённых миграций обновлён на 8
