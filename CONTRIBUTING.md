# Участие в разработке (CONTRIBUTING.md)

Спасибо за интерес к проекту POC Terminal Tracker! Проект распространяется под
лицензией **MIT** (см. `LICENSE`). Ниже — правила, которые нужно соблюдать при
подготовке изменений.

## Стек и требования

- **Язык:** C++17.
- **Фреймворк:** Qt 6 (Core, Gui, Widgets, Sql, PrintSupport, Charts, Network, Test).
- **БД:** PostgreSQL 17 (драйвер QPSQL).
- **Сборка:** CMake ≥ 3.20, `CMakePresets.json` (пресеты `dev-mingw`, `dev-linux`).
- **Форматирование:** `clang-format` (Qt-стиль, см. `.clang-format`).
- **Линтер:** `clang-tidy` (см. `.clang-tidy`).

## Сборка и запуск тестов

```powershell
# Windows (Qt 6.11.1 + MinGW 13.10)
cmake --preset dev-mingw
cmake --build build/dev-mingw

# Linux (системный Qt)
cmake --preset dev-linux
cmake --build build/dev-linux

# Тесты (требуют PostgreSQL 17 в PATH для интеграционных тестов)
ctest --test-dir build/dev-mingw --output-on-failure
```

Интеграционные тесты (`test_db_integration`, `test_backup_restore`,
`test_concurrency`) требуют работающего локального PostgreSQL и прав на
создание тестовых БД. Без PostgreSQL они завершаются `SKIP` (для них тест
не «краснеет»).

## Форматирование и линт

Перед отправкой PR убедитесь, что код отформатирован и не содержит новых
предупреждений линтера:

```bash
# Проверка форматирования (без применения изменений)
clang-format --dry-run -Werror $(git ls-files 'src/**/*.cpp' 'src/**/*.h' 'tests/**/*.cpp')

# Линт
clang-tidy src/**/*.cpp -- -std=c++17 ...
```

CI запускает `lint`-джоб (Linux): `clang-format --dry-run -Werror` +
`clang-tidy` по `src/`. Цель `lint` в CMake не влияет на обычную сборку.

## Политика PR

1. Ветка от `master`, PR с описанием «что» и «зачем».
2. **Один PR — одна задача** (или логически связанный набор).
3. Обязательные условия merge:
   - проект собирается (Windows и/или Linux);
   - `ctest` зелёный (интеграционные тесты могут быть SKIP при отсутствии PostgreSQL);
   - форматирование и линт проходят (`.clang-format`, `.clang-tidy`);
   - нет регрессий в тестах UI (`test_ui_components`).
4. Комментарии в коде — по-русски (стиль проекта).
5. Не коммитьте секреты: пароли, токены, `.env`, `config/config.json`.

## Требования к новым миграциям

1. Новый файл в `sql/migrations/NNN_описание.sql` с **следующим** номером
   (например, после `011_...` идёт `012_...`).
2. Миграция должна быть **идемпотентной** (`IF NOT EXISTS`, `DO $$ ... $$`).
3. **Не добавляйте** в миграции учётные данные (пароли, хеши) — дефолтная
   учётная запись admin создаётся приложением (см. `DatabaseManager::seedAdminAccount`).
4. При добавлении миграции обновите счётчики в тестах:
   `tests/test_db_integration.cpp` и `tests/test_concurrency.cpp`
   (ожидаемое количество записей в `schema_migrations`).
5. Транзакция управляется миграционным раннером — не вызывайте
   `BEGIN/COMMIT` внутри файла.

## Изменения схемы/данных

- Статусы терминалов: 0 = свободен, 1 = в аренде, 2 = в ремонте, 3 = списан,
  4 = утерян. Единый источник словаря — `src/utils/terminal_status.h`
  (`TerminalStatus::name`/`sqlCaseExpression`); не дублируйте имена статусов
  в SQL-запросах и формах.
- Слой данных: «сырой» SQL живёт в репозиториях (`src/database/repositories/`),
  данные передаются в UI value-моделями (`src/models/`). При добавлении новых
  запросов не пишите их прямо в формах — добавьте метод репозитория и, где
  уместно, value-модель.
- Деактивация терминалов: `tblterminals.is_deactivated = TRUE` вместо DELETE,
  если на терминал ссылаются документы.
- Изменение поведения форм — обязательно покрывать ручным чек-листом
  сценариев (приёмка → аренда → возврат) и, по возможности, автотестами.
