# Аудит проекта POC Terminal Tracker — 12.08.2026

## 1. Общая оценка

**Тип:** Десктопное приложение (Qt 6, C++17) для учёта POC-терминалов и SIM-карт.
**Бэкенд:** PostgreSQL 14+.
**Статус:** POC, версия 1.5.3, активная разработка.

---

## 2. Архитектура

### Сильные стороны
- Чёткое разделение на модули: `database/`, `ops/`, `update/`, `utils/`, `ui/`
- ADR-документация (5 записей) обосновывает ключевые решения
- Интерфейс `IDatabaseManager` + заглушка для тестирования — хороший паттерн
- Миграции БД с `pg_advisory_lock` защищают от гонок при одновременном старте
- `ConnectionPool` решает проблему Qt-соединений (одно на поток)
- Circuit Breaker защищает от каскадных сбоев БД
- `NOTIFY poc_data_changed` для межэкземплярного обновления дашборда

### Критические замечания
- 🔴 **MainWindow слишком большой (~1000 строк):** содержит логику UI, бэкапа, графиков, отчётов, глобального поиска. Требуется рефакторинг на компоненты/представления.
- 🔴 **Отсутствует слой моделей бизнес-сущностей:** все формы работают напрямую с `QSqlQuery`/`QSqlTableModel`. Это затрудняет тестирование и повторное использование логики.
- 🟡 **Hardcoded SQL-запросы в UI-коде:** `loadTopClients()`, `loadRecentDocuments()`, `updateCharts()` — SQL-строки разбросаны по `mainwindow.cpp`.

## 3. Безопасность

### Сильные стороны
- ✅ PBKDF2-HMAC-SHA256 (100k итераций) для хеширования паролей
- ✅ Constant-time сравнение хешей
- ✅ Rate limiting на уровне БД (5 попыток → 30 сек блокировка)
- ✅ Параметризованные запросы (SQL-инъекции устранены)
- ✅ SSL по умолчанию (`require`)
- ✅ SPKI-пиннинг сертификата для автообновлений
- ✅ SHA256-проверка бинарников обновлений
- ✅ HTTPS обязателен для `update.url`
- ✅ Ролевая защита на уровне БД (триггеры `enforce_user_management`, `enforce_audit_log_protection`)
- ✅ Шифрование бэкапов AES-256-CBC
- ✅ Принудительная смена пароля для legacy-хешей и дефолтного admin

### Критические проблемы
- 🔴 **Дефолтный пароль admin захардкожен в миграции 001_initial.sql:** хеш SHA-256 от `admin123` известен публично из репозитория. Хотя миграция 009 ставит `must_change_password=TRUE`, сам факт наличия хеша дефолтного пароля в коде — антипаттерн.
- 🔴 **Пароль БД передаётся в `BackupWorker::ConnectionParams` по открытому каналу:** `params.password` копируется в фоновый поток через сигнал/слот. В Qt queued-сигналы сериализуют `QString`, но это всё равно не шифрованный канал.
- 🟡 **Passphrase для шифрования бэкапа вводится в `QInputDialog` и хранится в памяти:** `m_backupPassphrase` в `OpsScheduler` — не очищается после использования.
- 🟡 **`.env` ищется в нескольких каталогах, но не проверяются права доступа:** на Linux файл `.env` с паролем может быть доступен другим пользователям.

## 4. Надёжность

### Сильные стороны
- ✅ Retry transient-ошибок (до 3 попыток, backoff)
- ✅ Circuit Breaker (5 сбоев → 30 сек cooldown)
- ✅ Graceful shutdown через `aboutToQuit`
- ✅ Fallback-дамп при недоступности `pg_dump`
- ✅ `--single-transaction` при восстановлении
- ✅ Конкуренто-тесты покрывают гонки (SIM, аренда, rate limiting, миграции)

### Критические проблемы
- 🔴 **`DatabaseManager::getDatabase()` возвращает неконстантную ссылку:** любой вызывающий может вызвать `close()` или изменить состояние соединения без контроля.
- 🔴 **`executeQuery()` не проверяет `QSqlQuery::isActive()` после `exec()`:** если query вернул результат (SELECT), код вызывающий `executeQuery` может не проверить, был ли вызван `next()`.
- 🟡 **`BackupManager::createFallbackBackup()` генерирует SQL-дампы через `INSERT`:** при больших объёмах данных (100k+ строк) это крайне медленно и создаёт огромный SQL-файл.
- 🟡 **Нет проверки целостности `.xlsx`-файлов:** `ReportExporter::exportModelToExcel()` не проверяет, не занят ли файл другим процессом.

## 6. Код-стайл и качество

### Сильные стороны
- ✅ Комментарии на русском, объясняющие *зачем*
- ✅ Редкие, но информативные комментарии в сложной логике
- ✅ Именованные константы (`constexpr`) для таймаутов и ключей
- ✅ `QMutexLocker` для RAII-синхронизации
- ✅ `std::function` для фабрик и транзакций

### Критические проблемы
- 🔴 **`CheckBoxDelegate` использует `Qt::DisplayRole` для хранения булева значения:** это нарушает конвенцию ADR-0004 (должен использоваться `Qt::CheckStateRole`). При использовании `QSqlTableModel` это может привести к потере данных при сохранении.
- 🔴 **`ComboBoxDelegate::setModelData` записывает ID в `Qt::UserRole` и текст в `Qt::DisplayRole`, но `QSqlTableModel::setData` не знает об этой конвенции:** при `submitAll()` в БД может записаться текст вместо ID.
- 🟡 **`MainWindow` содержит ~1000 строк:** нарушает SRP. Следует разбить на `DashboardView`, `ChartPanel`, `ReportDialog` и т.д.
- 🟡 **Много `#include` в `mainwindow.cpp` (~60 строк):** следует использовать forward declarations для типов, которые не нужны в заголовочной части.
- 🟡 **`formatSqlValue()` в `backupmanager.cpp` не обрабатывает все типы PostgreSQL:** `QByteArray` форматируется как hex-строка, но бинарные данные (`bytea`) могут содержать нуль-байты, которые `QTextStream` обрежет.

## 7. SQL и база данных

### Сильные стороны
- ✅ Идемпотентные миграции (`IF NOT EXISTS`, `CREATE OR REPLACE`)
- ✅ Транзакционные миграции (версия записывается в той же транзакции)
- ✅ Индексы на всех ключевых колонках
- ✅ CHECK-ограничения на статусы
- ✅ Триггеры аудита на `tblterminals` и `tblclients`
- ✅ Ролевая защита через триггеры БД

### Критические проблемы
- 🔴 **`000_base_schema.sql` определяет `CHECK (status IN (0,1,2))`, но `006_terminal_status_check.sql` расширяет до `(0,1,2,3,4)`:** на чистой БД, собранной из миграций, `000` создаст ограничение `(0,1,2)`, а `006` его расширит. Но если кто-то применит только `000` — статусы 3 и 4 сломаются. Это не баг, но документация должна это отражать.
- 🟡 **`tblterminals.status` — `SMALLINT` с числовыми значениями:** лучше использовать `VARCHAR` или `ENUM` для лучшей читаемости.
- 🟡 **Нет `ON DELETE CASCADE` для `tblrentaldetails → tblterminals`:** при удалении терминала аренда остаётся с `NULL`-terminalid. Это может быть намеренным (архивирование), но требует документирования.
