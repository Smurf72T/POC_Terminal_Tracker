# Аудит проекта POC Terminal Tracker — 12.08.2026

> Обновлено по итогам верификации по коду (12.08): некорректные пункты удалены, добавлены подтверждённые находки (печать накладной, «деактивация» терминала, редактируемые статусы и др.).

## 1. Общая оценка

**Тип:** Десктопное приложение (Qt 6, C++17) для учёта POC-терминалов и SIM-карт.
**Бэкенд:** PostgreSQL 14+ (в CI проверено на 17).
**Статус:** POC, версия 1.5.3, активная разработка.

---

## 2. Архитектура

### Сильные стороны
- Чёткое разделение на модули: `database/`, `ops/`, `update/`, `utils/`, `ui/`
- ADR-документация (5 записей в `docs/adr/ADR-0001.md`) обосновывает ключевые решения
- Интерфейс `IDatabaseManager` + заглушка для тестирования — хороший паттерн
- Миграции БД с `pg_advisory_lock` защищают от гонок при одновременном старте
- `ConnectionPool` решает проблему Qt-соединений (одно на поток)
- Circuit Breaker защищает от каскадных сбоев БД
- `NOTIFY poc_data_changed` для межэкземплярного обновления дашборда

### Критические замечания
- 🔴 **MainWindow слишком большой (~1370 строк):** содержит логику UI, бэкапа, графиков, отчётов, глобального поиска. Требуется рефакторинг на компоненты/представления.
- 🔴 **Отсутствует слой моделей бизнес-сущностей:** все формы работают напрямую с `QSqlQuery`/`QSqlTableModel`. Это затрудняет тестирование и повторное использование логики.
- 🟡 **Hardcoded SQL-запросы в UI-коде:** `loadTopClients()`, `loadRecentDocuments()`, `updateCharts()` — SQL-строки разбросаны по `mainwindow.cpp`.

## 3. Безопасность

### Сильные стороны
- ✅ PBKDF2-HMAC-SHA256 (100k итераций) для хеширования паролей
- ✅ Constant-time сравнение хешей
- ✅ Rate limiting на уровне БД (5 попыток → 30 сек блокировка)
- ✅ Параметризованные запросы (SQL-инъекции устранены)
- ✅ SSL по умолчанию (`require`)
- ✅ SPKI-пиннинг сертификата для автообновлений
- ✅ SHA256-проверка бинарников обновлений
- ✅ HTTPS обязателен для `update.url` (http разрешён только для localhost/127.0.0.1)
- ✅ Ролевая защита на уровне БД (триггеры `enforce_user_management`, `enforce_audit_log_protection`)
- ✅ Шифрование бэкапов AES-256-CBC
- ✅ Принудительная смена пароля для legacy-хешей и дефолтного admin (миграция 009)

### Критические проблемы
- 🔴 **Дефолтный пароль admin захардкожен в миграции `001_initial.sql`:** хеш дефолтного пароля лежит в репозитории — при известном пароле возможен офлайн-подбор. Миграция 009 ставит `must_change_password=TRUE` (подтверждено по коду), но сам факт наличия дефолтных учётных данных в коде — антипаттерн. Рекомендация: генерировать пароль при bootstrap и выводить один раз.
- 🔴 **Self-registration без ограничений:** `LoginForm::on_btnRegister_clicked` создаёт учётные записи без rate-limit и без капчи. Смягчение: аккаунты создаются неактивными (`is_active=FALSE`) и активируются администратором — канал спама открыт, но доступ ограничен модерацией.

### Проблемы (некритические)
- 🟡 **Passphrase бэкапа в аргументах командной строки `openssl`:** `backupmanager.cpp:101,173` передаёт passphrase через `-pass pass:...` — значение видно в списке процессов (Linux: `/proc/<pid>/cmdline`). Рекомендация: `-pass stdin`.
- 🟡 **Пароль БД для `pg_dump`/`psql` через env-переменную `PGPASSWORD`:** `backupmanager.cpp:254,497` — читается любым процессом того же пользователя (Linux: `/proc/<pid>/environ`). Стандартная практика, но альтернатива — `~/.pgpass` с правами 600.
- 🟡 **Passphrase и пароль БД хранятся в памяти** (`OpsScheduler::m_backupPassphrase`, строка в `backupRequested` queued-сигнале) и не очищаются после использования.
- 🟡 **`.env` ищется в нескольких каталогах, но права доступа не проверяются:** на Linux файл `.env` с паролем может быть доступен другим пользователям.

## 4. Надёжность

### Сильные стороны
- ✅ Retry transient-ошибок (до 3 попыток, backoff)
- ✅ Circuit Breaker (5 сбоев → 30 сек cooldown)
- ✅ Graceful shutdown через `aboutToQuit`
- ✅ Fallback-дамп при недоступности `pg_dump`
- ✅ `--single-transaction` при восстановлении
- ✅ Таймауты на `pg_dump`/`psql`/`openssl` (60/120/60 с) с kill
- ✅ Конкуренто-тесты покрывают гонки (SIM, аренда, rate limiting, миграции)

### Проблемы (некритические)
- 🟡 **Зависание при выходе:** `m_backupThread->wait()` без таймаута в `MainWindow::~MainWindow` (mainwindow.cpp:212) и `OpsScheduler::~OpsScheduler` (opsscheduler.cpp:78) — при активном restore/бэкапе приложение может блокироваться на время операции (или дольше при зависшем `psql`).
- 🟡 **Дублирование `ensureBackupWorker()`:** логика создания `BackupWorker`/`QThread` продублирована в `mainwindow.cpp:1004` и `opsscheduler.cpp:198` — при правке нужно помнить о двух местах.
- 🟡 **`OpsScheduler` тикает в никуда:** при выключенных backup и integrity `rescheduleTimer()` всё равно перезапускает таймер на 60 с (opsscheduler.cpp:179,195).
- 🟡 **Нет таймаута на сетевые запросы `UpdateManager`:** `m_nam.get()` в `checkForUpdates`/`downloadUpdate` (updatemanager.cpp:120,207) без `setTransferTimeout` — при зависшем сервере проверка обновлений «висит» бесконечно.
- 🟡 **`DatabaseManager::getDatabase()` возвращает неконстантную ссылку:** любой вызывающий может вызвать `close()` или изменить состояние соединения без контроля.
- 🟡 **`executeQuery()` не проверяет `QSqlQuery::isActive()` после `exec()`:** корректность работы зависит от вызывающего кода.
- 🟡 **`createFallbackBackup()` генерирует SQL-дампы построчно через `INSERT`:** при больших объёмах данных (100k+ строк) это крайне медленно и создаёт огромный SQL-файл.
- 🟡 **Нет проверки результата `ReportExporter::exportModelToExcel()`:** при занятом `.xlsx`-файле возврат `false` игнорируется в `reportsform` — пользователь не узнаёт об ошибке.

## 5. Тестирование

| Группа | Название | Ключевые проверки |
|--------|----------|-------------------|
| SQL | `TestDatabase` | Параметризация, инъекции, миграции на чистой БД |
| DB | `TestDbIntegration` | Полный сценарий: создание/аренда/возврат, роли, rate limiting, документы, бэкапы |
| Sim | `TestSimOperations` | Выдача/освобождение, проверка совпадений IMEI |
| Update | `TestUpdateManager` | SHA256, SPKI-пиннинг, rollback |
| Backup | `TestBackupRestore` | `pg_dump`/`psql` restore, fallback-дамп, шифрование, roundtrip |
| UI | `TestUiComponents` | Кастомные делегаты, ввод |

### Проблемы
- 🟡 **Roundtrip-тест бэкапов существует, но требует инструментов PostgreSQL:** `test_db_integration::test_backup_and_opslog` покрывает fallback-дамп, `createBackup` (pg_dump/fallback), AES-шифрование и restore в свежую БД (create→restore→проверка данных). На машинах без `pg_dump`/`psql` в PATH падает.
- 🟡 **Нет тестов для `Validator::checkUniqueSerial` и `checkDuplicateIMEI`:** методы ходят в БД через `databaseManager()`, но конфликты уникальности не покрыты.
- 🟡 **Нет тестов для `ReportExporter`:** экспорт в Excel/PDF не покрыт.
- 🟡 **Нет тестов для `LoginForm`:** логика входа, смены пароля, rate limiting — только в `test_db_integration`.

## 6. Баги в UI-формах и отчётах (верифицировано по коду 12.08.2026)

- 🔴 **Печать накладной: поле «Модель» пустое** (`receiptform.cpp:387-388`). При формировании HTML печать читает `DisplayRole` (текст модели) и конвертирует в `int` (→ 0); ID модели лежит в `Qt::UserRole` (строка 231 при сохранении читает `UserRole` корректно). Результат — в печатной накладной колонка «Модель» пуста.
- 🟡 **«Деактивация» терминала на деле — `DELETE`** (`terminalsform.cpp:263-275`). Если на терминал ссылаются документы, UI обещает «деактивацию», но выполняет `DELETE FROM tblterminals`, который падает на `ON DELETE RESTRICT` (tblreceiptdetails/tblrentaldetails/tblreturndetails). Пользователь получает ошибку «не удалось деактивировать», терминал остаётся в БД. Нет реального флага деактивации.
- 🟡 **Массовое обновление статусов: неверный текст подтверждения** (`batchstatusform.cpp:93`). `statusText` возвращает «Свободен» только для 0, для всех остальных статусов (1, 2, 3, 4) — «В аренде». Диалог подтверждения для статусов 2/3/4 показывает неверное значение.
- 🟡 **Прямое изменение статусов в обход бизнес-логики:**
  - `SIMCardsForm` — колонка «Статус» редактируемая (`simcardsform.cpp:51`, `QSqlTableModel::OnFieldChange`); делегат `SimStatusDelegate` меняет только отображение, поэтому статус SIM можно сменить вручную, минуя документы аренды/возврата.
  - `BatchStatusForm` — позволяет выставить статус «В аренде» (1) напрямую, без создания документа аренды; ролевая проверка не выполняется.
- 🟡 **Отчёт «Терминалов в аренде» неточный** (`reportsform.cpp:69-74`). Считается `COUNT(DISTINCT rd.terminalid)` по всем когда-либо арендованным терминалам клиента без фильтра по датам и без учёта текущего статуса — цифра не отражает фактическую загрузку.
- 🟡 **PaymentForm: в режиме редактирования нет проверки дубликата** (`paymentform.cpp:251-279`). При создании вызывается `checkExistingPayment` (строка 282), при редактировании — нет: можно сохранить второй платёж за тот же (клиент, месяц, год) либо получить ошибку БД при наличии уникального ограничения.
- 🟡 **`--check-db` применяет миграции** (`main.cpp:96-97`). «Проверка» не является read-only: `initialize()` применяет pending-миграции. Также ветка `DB_WARN` (`pendingMigrations`) практически недостижима, так как миграции уже применены.

## 8. SQL и база данных

### Сильные стороны
- ✅ Идемпотентные миграции (`IF NOT EXISTS`, `CREATE OR REPLACE`)
- ✅ Транзакционные миграции (версия записывается в той же транзакции)
- ✅ Индексы на всех ключевых колонках
- ✅ CHECK-ограничения на статусы
- ✅ Триггеры аудита на `tblterminals` и `tblclients`
- ✅ Ролевая защита через триггеры БД
- ✅ FK-ограничения с осознанными `ON DELETE` (RESTRICT для документов, SET NULL для SIM)

### Критические проблемы
- 🟡 **`000_base_schema.sql` определяет `CHECK (status IN (0,1,2))`, но `006_terminal_status_check.sql` расширяет до `(0,1,2,3,4)`:** на свежей БД, собранной из всех миграций, ограничение корректно. Но если кто-то применит только `000` — статусы 3 и 4 сломаются. Требует документирования (не баг).
- 🟡 **`tblterminals.status` — `SMALLINT` с числовыми значениями:** лучше использовать `VARCHAR` или `ENUM` для лучшей читаемости.
